核心板块 1

运行视图：先确认面板新鲜，再相信结论。

运行视图把工作台顶部、每日资产账本、Token 筛选和后台流水线放在一起，回答一个问题：当前面板是否值得继续读。

1

按四步读

  • 顶部和快照：确认版本、更新状态和生成时间；快照旧就先刷新。
  • 每日资产账本：先看当天产出了什么，再看右侧工作窗口、上下文和 Token 数。
  • Token 筛选：先定来源、日期范围和粒度，再判断模型任务是否过重。
  • 后台流水线：看阶段、上次运行、下次运行和失败提示，再判断是否是记忆或资产逻辑问题。
运行模块

Token：先看消耗，再决定是否扩大范围。

Token 模块用来看本机使用趋势，不是账单页；把它当成 Codex / Claude Code 活动的成本和压力信号。

1A

它适合看成本感知，不必每天盯。

  • 来源：想知道压力来自哪个 host 时，再切全部 / Codex / Claude。
  • 粒度：按日看短期峰值；按月看长期趋势和来源对比。
  • 日期范围：先选能回答问题的最小范围，再看总量。
  • 构成：如果缓存或输出突然变多，再回看近期任务是否改变了模型行为。
运行模块

后台运行监控：判断自动整理有没有正常工作。

当面板看起来过旧、记忆没有出现，或者你想确认定时刷新是否真的跑过，就看后台运行监控。

1B

先看状态，再决定是否手动触发。

  • 当前状态：Completed 表示流水线完成；Failed 时先看失败阶段，不要先改配置。
  • 下次运行：判断等下一次定时刷新是否就够了。
  • 阶段检查：定位问题在采集、整理、索引、host 摘要同步、资产刷新还是面板重建。
  • 历史记录：同一阶段反复失败，比单次快照旧更值得排查。
核心板块 2

个人资产记忆：留下有用经验，清掉噪声。

这里是管理 OpenRelix 个人资产记忆的主入口：看哪些记忆被生成、哪些有用、哪些该隐藏，以及哪些可能进入 host context。

2A

先读卡片，再用反馈训练面板。

  • UI：每张卡片是一条从本机工作中提炼出的可复用偏好、规则、手册、项目习惯或任务簇。
  • 有用：保留并强化这条记忆，后续摘要和面板排序会更愿意采用它。
  • 无用：把噪声候选从当前视图移走，避免过期或误生成的记忆长期占位置。
  • 生成原理：OpenRelix 读取近期窗口，用大模型归纳可复用规则，再写成本地结构化记忆。
  • 注入原理：只有记忆模式允许时，OpenRelix 才把有界摘要同步到受控 host-context 块；原始窗口仍留在本地。
  • 成本：记忆生成由大模型完成，会消耗 token。如果暂时只想看面板，可以关闭记忆模式。
openrelix mode off
核心板块 2B

原生记忆：看 Codex 和 Claude 自己记住了什么。

原生记忆视图是对照视图。它帮助你看清 host 自己能直接读到什么，以及 OpenRelix 个人资产记忆在哪些地方只是本地补充。

2B

用它检查 host 边界。

  • Codex 原生记忆：展示 Codex 侧可读的记忆，包括启用时的 OpenRelix 受控摘要块。
  • Claude 原生记忆：当本机能读取 Claude Code 活动时，展示 Claude Code 侧的记忆来源。
  • 提取原理：OpenRelix 读取 host 自己拥有的记忆文件、受控块和本地展示缓存，再整理成面板可读格式。
  • 边界：OpenRelix 不会把每个原始窗口都塞进 host 原生记忆；只有当前模式允许时才同步自己的受控摘要。
  • 使用场景：当 agent 漏掉稳定规则、重复旧问题时，用它对比原生记忆和个人资产记忆差在哪里。
核心板块 3

资产层：先看存量，再决定升级什么。

资产层不是记忆注入层，而是可复用材料盘点：登记册资产、已发现资产、复盘、复用事件和仓库范围资产都在这里看。

3

先看盘点，再看工具热度

  • 登记册资产：只统计写入 registry/assets.jsonl 的稳定资产，这是刻意沉淀的书架。
  • 已发现资产：扫描到的 skills、提示词、Rules、插件、启动项，以及近期被读取的项目 skills。
  • 资产筛选：日期范围会影响工具热度、活跃度和趋势解读，不代表全部历史消失。
  • 升级判断：只有有用、可复用、下次任务也看得懂的内容，才值得升级成正式资产。
核心板块 4

工具热度：优化 agent 真正在用的东西。

工具热度展示 skills 和 MCP 工具的真实使用信号。用它决定哪些能力值得补文档、模板、示例，哪些该清理。

4

重点看三种模式

  • 7 天和 30 天都高：这是正在活跃的工作流，优先补文档和示例。
  • 30 天高但 7 天低：可能开始过期，要看工作流是否已经变化。
  • MCP 工具突然变热：回到窗口层看它是真有用，还是失败后反复重试。
  • 低频但高价值：先留本地，等另一个任务证明它值得升级。
核心板块 5

复盘记录：把做完的事变成可复用资产。

复盘记录不是原始日志，而是资产化入口。它展示哪些任务产出了稳定 playbook、skill、template、automation 或 checklist。

5

任务有复用价值时才复盘

  • 当任务产出稳定方法、排障路径、模板或检查清单时，再做复盘。
  • 看复用事件，确认某个已有资产是否真的帮助了后续任务。
  • 新环境里复盘区域为空是正常的，表示还没有保存过复盘产物。
  • 一次有价值复盘后，要确认登记册、使用事件和 overview 都更新了。
核心板块 6

窗口层：把结论追溯到真实工作上下文。

窗口层是证据层。先用窗口总览定位项目和任务；只有需要原始证据时，再打开窗口明细。

6

不要逐条翻，先定位再下钻

  • 窗口筛选：尤其在长周期回溯后，先按日期缩小范围。
  • 窗口地图：用项目数、并行任务、窗口数和讨论数定位工作密集区。
  • 追溯按钮：从聚合任务跳到对应窗口明细，不要从头扫所有卡片。
  • 窗口明细：验证某条记忆、复盘结论或工具热度信号为什么存在。
窗口明细

窗口明细：需要证据时，再看单次任务。

窗口明细用于核验，不是每天逐条浏览。只有想知道某条记忆、复盘或工具热度信号为什么出现时，再进入这里。

7

把明细当证据页，不当列表刷。

  • 先看任务标题和来源元数据：host、采集来源、时间、工作目录能说明信号从哪里来。
  • 问题和结论要一起看；脱离问题的结论很容易被误读。
  • 当记忆候选看起来不对、复盘结论需要证明、某个工具热度条目异常时，再打开明细。
  • 不要逐条读完所有卡片；明细回答了具体疑问，就回到总览。
日常使用

保持一个很简单的节奏。

OpenRelix 最好用的方式，是让例行任务做重复工作；你只在要复盘、升级资产或排障时介入。

打开面板

先看运行视图，不要先翻记忆。

先确认快照时间、后台状态和 Token 压力，再解读记忆或资产结论。

去运行视图
可复用任务

任务刚结束时复盘。

如果产出了方法、清单、模板或排障路径，趁上下文还新鲜时沉淀。

去复盘记录
结果不对

从后台状态追到窗口证据。

记忆或资产结论不对时，先看流水线，再追原始窗口。

去后台监控
工作中

正常使用 AI agent

OpenRelix 之后读取本地保存的 host 活动；你不需要把每段对话另存到别的工具里。

任务后

可复用任务就做一次即时复盘

当任务产出了方法手册、skill、模板、自动化、检查清单或稳定排障路径时，用 memory-review 复盘。

memory-review
默认 60 分钟

面板刷新可以自动跑

overview LaunchAgent 默认每 60 分钟刷新面板。安装完成后，用 schedule 直接调整已安装的 LaunchAgent 间隔。

openrelix schedule --overview-refresh-interval-minutes 30
夜间

当天窗口分阶段整理

默认 23:00 生成当天预览，00:10 生成前一日终版。安装完成后，用 schedule 直接调整这两个 LaunchAgent 时间。

openrelix schedule --nightly-organize-time 22:30 --nightly-finalize-time 01:00
常见问题

遇到异常时，先查最窄的证据。

目标是少猜。下面这些检查能把第一轮排障收在本机、收在具体链路上。

面板为空

先查采集

先跑 app-server 检查；如果 Codex app-server 不可用，OpenRelix 应尽量回退到 history/session。

再看后台监控
openrelix doctor --app-server-check
记忆没刷新

查模型认证

学习刷新依赖配置好的 model CLI；改记忆设置前先确认模型链路能跑。

再看记忆导览
openrelix doctor --model-check
升级修复

重同步本地集成

当 npm 包已是最新但 app、LaunchAgent 或面板像是旧的，走 force 修复路径。

再看运行视图
openrelix update --yes --force
时间不合适

按节奏调整定时任务

夜间预览默认 23:00，面板刷新默认 60 分钟。默认节奏不适合时，从日常使用里的指令调整。
